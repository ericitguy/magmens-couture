# Magmens Couture

The website for **Magmens Couture**, a Ghanaian luxury bridal and couture fashion
house in Obuasi New Estate, Ashanti Region.

> Redefining Elegance Through Craftsmanship.

Next.js 15 (App Router) · TypeScript · Tailwind CSS v4 · server-side enquiry
handling · a small, dependency-light photography pipeline.

## Quick start

```bash
npm install
npm run dev        # http://localhost:4310
```

Other scripts:

| Script | Purpose |
| --- | --- |
| `npm run build` | Production build |
| `npm start` | Serve the production build on port 4310 |
| `npm run typecheck` | `tsc --noEmit` |
| `npm run lint` | ESLint (Next core-web-vitals + TypeScript) |
| `npm run images` | Rebuild the photography derivatives and social cards |
| `npm run enquiries` | Print recent enquiries from the local file store |

Node 24 is required. It is pinned in `package.json` (`engines`) and in `.nvmrc`,
so `nvm use` selects the right version locally and Vercel builds on the same
major version.

## Environment variables

Copy `.env.example` to `.env.local` for development, and set the same names in
the hosting dashboard for production. Full explanations live in
[.env.example](.env.example); the short version:

| Variable | Required | What it does |
| --- | --- | --- |
| `NEXT_PUBLIC_SITE_URL` | Yes | Canonical URLs, sitemap, `robots.txt`, social previews |
| `DATABASE_URL` | Yes for launch | Neon serverless PostgreSQL — where enquiries are stored |
| `RESEND_API_KEY` | Recommended | Enables studio email alerts for new enquiries |
| `ENQUIRY_NOTIFICATION_EMAIL` | Recommended | The studio inbox that receives those alerts |
| `ENQUIRY_FROM_EMAIL` | After domain verification | The verified sender address |
| `CALENDAR_FEED_TOKEN` | Recommended | Unlocks the private calendar feed of bookings |
| `ADMIN_ACCESS_TOKEN` | Optional | Unlocks `/admin/enquiries?token=…` |

Nothing here is exposed to the browser except `NEXT_PUBLIC_SITE_URL`.

## How the site is put together

```
photos/                     Original camera and phone files (never modified)
public/
  photography/              Optimised web masters, generated by `npm run images`
  og/                       Per-photograph 1200×630 social cards
scripts/
  prepare-images.mjs        The photography pipeline
  list-enquiries.mjs        Terminal view of the local enquiry store
src/
  app/                      Routes: pages, API handlers, sitemap, robots, 404
  components/
    layout/                 Announcement bar, header, footer, WhatsApp entry
    sections/               Page-level editorial blocks
    gallery/                Filterable gallery and lightbox
    forms/                  Consultation and contact forms, field primitives
    media/                  Image components (parallax, editorial image)
    ui/                     Buttons, headings, containers, reveal, monogram plate
    seo/                    JSON-LD renderer
  content/                  ← everything the studio is likely to change
  lib/                      Validation, storage, notifications, structured data
```

### The content folder is the control panel

Almost every word, photograph reference and policy on the site comes from
`src/content`:

| File | What lives in it |
| --- | --- |
| `site.ts` | Brand copy, tagline, contact details, social profiles, form options, navigation |
| `collections.ts` | The four collections: copy, characteristics, imagery, enquiry routing, SEO |
| `gallery.ts` | The curated gallery: which photographs exist and how each is described |
| `image-manifest.json` | **Generated.** Dimensions and blur placeholders for each photograph |
| `story.ts` | Founder biography, timeline, craft pillars, pull quotes |
| `journey.ts` | The four-step bespoke process, and the testimonial list |
| `policies.ts` | The twelve official policies, version and last-updated date |
| `payments.ts` | Published payment methods, Mobile Money and bank details |
| `faq.ts` | Frequently asked questions, grouped by topic — also feeds FAQ structured data |
| `privacy.ts` | The privacy notice |

Because these are typed modules, a typo in an image slug or a missing
photograph fails the build instead of shipping a broken page.

## Updating the website

**Change a policy.** Edit `src/content/policies.ts`, then update `version` and
`lastUpdated` in the same file. The policies page and the footer both read from
it.

**Edit an FAQ answer.** `src/content/faq.ts` is grouped by topic and renders on
`/faq`, in the footer and in the FAQ structured data search engines read. Every
answer restates a policy, the booking process or a payment rule, so when a term
changes, change it in `policies.ts` (or `payments.ts`) *and* here — the site must
never give two versions of the same rule. Do not add lead times, prices or
services the studio has not confirmed.

**Edit the payment details.** `src/content/payments.ts` holds the Mobile Money
number, the bank account and the payment rules. The policies page shows them
inside the payment section automatically. Only ever publish the studio's own
verified details: a wrong account number is a fraud risk, not a typo.

**Add an award or recognition.** Append to the `awards` array in
`src/content/story.ts` — year, title, awarding body and one line of context. The
founder page renders them as a numbered grid, newest first.

**Replace the logo.** Overwrite `public/brand/magmens-monogram.png` (square PNG),
then regenerate the favicons from it: `src/app/icon.png` at 512×512 and
`src/app/apple-icon.png` at 180×180. The founder brand plate uses the same file.

The header lockup is not that square: it pairs the studio's MC emblem with the
name set in type, because the circular artwork is unreadable below ~110px. Both
emblem files are cut from the supplied logo artwork by
`npm run brand:assets -- "more photos/logo.PNG"`:
`magmens-emblem.png` (ink, for ivory surfaces) and `magmens-emblem-inverse.png`
(single ivory ink, for the transparent header over a hero photograph). Rerun it
if the artwork changes, and add `showMark` to a `<Wordmark>` to use the emblem
anywhere else.

**Add a testimonial.** Genuine, approved reviews only. Add them to the
`testimonials` array in `src/content/journey.ts` and the placeholder section
becomes an editorial testimonial grid automatically.

**Add studio opening hours.** Set `hours` in `src/content/site.ts` (for example
`"Monday – Friday, 9:00 – 17:00"`). The contact page and the structured data
will pick it up. Structured data deliberately omits hours until this is set.

**Update a social link.** Set `url` in the `socials` array in
`src/content/site.ts`. While a URL is `null` the profile name is shown as plain
text — the site never links to a guessed destination.

**Add or replace a photograph.** See the next section.

**Add the founder portrait.** Put the file in `./photos`, add it to `SOURCES` in
`scripts/prepare-images.mjs` with a descriptive slug (for example
`founder-portrait`), add a matching entry to `src/content/gallery.ts` with
descriptive alt text, run `npm run images`, then set `founder.portraitSlug` in
`src/content/story.ts`. The monogram plate on the homepage and the founder page
is replaced by the photograph.

**Add an award photograph.** Drop the file into `./photos` with a descriptive
name, add it to the `SOURCES` list in `scripts/prepare-images.mjs` with the
matching award slug, add a `gallery.ts` entry whose `tags` include
`"occasion"` or `"atelier"` so it appears in the public gallery, run `npm run
images`, then add an `image` field to the award in `src/content/story.ts`:
the section renders one photo per award by matching `image` to the slug.
Verify the award's name in the photo first — each award entry references one
verified image only.

The current portrait is the studio's photograph of Marian in the red sequin
gown, which is already prepared for the reception and occasion-wear galleries —
so it reuses that master (`reception-red-sequin-ruffle`) instead of a duplicate.
Its gallery entry names her, and the founder frame is 2:3 to match the file, so
replacing this one needs a photograph of the same proportions to stay uncropped.

**Change a collection's copy or imagery.** Edit
`src/content/collections.ts` — `intro`, `characteristics`, `galleryImages`,
`note`, SEO title and description all live there.

## Photography

The originals supplied by the studio total roughly 45 MB, which is far too heavy
to serve directly. `npm run images` (`scripts/prepare-images.mjs`) produces:

- a web master per photograph, longest edge 2400px, WebP quality 82, EXIF
  orientation applied, average ~180 KB;
- a base64 blur placeholder embedded in `src/content/image-manifest.json`, so
  images arrive gracefully and never shift the layout;
- per-photograph 1200×630 JPEG social cards in `public/og`;
- and the branded card in `public/og/magmens-couture.jpg`.

The pipeline also **detects and removes letterbox bars**. One supplied file was
a phone screenshot with black bands top and bottom; they are trimmed
automatically (a second pass catches the rounding remainder), and the script
reports what it removed. It refuses to trim when doing so would remove more than
a fifth of the frame, so genuinely dark photographs are left alone.

To add photography:

1. Drop the file into `./photos` (originals are never modified).
2. Add `{ source: "filename.jpg", slug: "descriptive-slug" }` to `SOURCES`.
3. Run `npm run images`.
4. Describe it in `src/content/gallery.ts` (alt text, caption, longer
   description, collection tags).

**Alt text matters.** Each gallery entry carries a specific description of the
garment, the client and the setting, written for screen-reader users. Keep that
standard when adding new work.

## Consultation & contact system

Both forms post to a server route (`/api/booking`, `/api/contact`) that runs the
same validation the browser ran, then stores the enquiry and notifies the studio.

**Validation.** `src/lib/validation.ts` holds Zod schemas shared by the browser
and the server. Server-side validation is authoritative; the client-side pass
exists only to give fast feedback.

**Spam protection.** Three layers: a honeypot field, a minimum fill time (a
submission completed in under 2.5 seconds is refused), and an in-memory rate
limit (6 consultation requests or 8 contact messages per client per 15 minutes,
returning HTTP 429 with `Retry-After`). The limiter is per server instance and
is documented as such — a durable store is the upgrade path if abuse ever
becomes a problem.

**Storage.** With `DATABASE_URL` set, records go to an `enquiries` table in
Neon; the schema is created on first use and every value is written as a bound
parameter. Without it, records are appended to `data/enquiries.jsonl` so the
forms are fully functional on a developer machine. On a serverless host the disk
is read-only, so a database is required for production; when storage fails the
endpoint returns HTTP 503 and a clear message rather than pretending to succeed.

**Notifications.** With `RESEND_API_KEY` and `ENQUIRY_NOTIFICATION_EMAIL` set, an
email is sent to the studio through Resend, with `reply-to` set to the enquirer.
An attached inspiration image (up to 4 MB) is attached to that email. Until the
keys are set, the enquiry is stored, the admin view flags that email alerts are
off, and no email is claimed to have been sent.

**Admin view.** `/admin/enquiries?token=YOUR_ADMIN_ACCESS_TOKEN` lists the stored
requests. The token is compared in constant time and the route returns 404
without a match. The page is `noindex` and disallowed in `robots.txt`.

### The booking promise

The system never claims an appointment is confirmed. A submission returns
`status: "received"`, is stored as `pending_confirmation`, and the confirmation
screen states plainly that the studio reviews each request and replies directly
with availability, and where applicable the consultation fee and payment
instructions. No fee, slot, account number or automatic payment is invented
anywhere in the code.

**Inspiration images** are stored in the database (base64) or, on the file
store, under `data/uploads/`. That is appropriate for a boutique studio's
volume; a bucket (Cloudflare R2 or S3) is the upgrade path if volumes grow.

### Bookings on the studio's calendar

Requests reach a calendar in three ways, all standard ICS, so Google Calendar,
Apple Calendar and Outlook work without an OAuth app or a paid integration:

1. **The studio subscribes once.** Set `CALENDAR_FEED_TOKEN`
   (`openssl rand -hex 32`), open `/admin/enquiries?token=…`, and copy the feed
   address shown there. Add it in Google Calendar under *Other calendars → From
   URL*, in Apple Calendar under *File → New Calendar Subscription*, or in
   Outlook under *Add calendar → Subscribe from web*. Every new consultation
   request then appears automatically, refreshed hourly, marked **tentative**.
2. **The alert email carries an invitation.** When Resend is configured, the
   studio's notification includes a `.ics` attachment for the requested slot, so
   it can be added to any calendar straight from the inbox.
3. **The client gets the same slot.** The confirmation screen offers
   *Add to my calendar*, which downloads the requested date and time. Requests
   without a preferred date have nothing to schedule and no link is shown.

Ghana is UTC+0 all year, so studio times are written as UTC stamps — correct in
any calendar, in any country, with no time-zone database needed. Each entry
records the request reference, occasion, collection, method and event date, and
states that the appointment is not yet confirmed. The feed contains real client
names, so treat its URL as a password: without the token the route returns 404.

Requests are read from the same store as the admin view, so the feed only works
once `DATABASE_URL` is set on the host. A local dev server shows local records.

## Before launch

These are the things only the studio can supply or approve:

1. **Set `DATABASE_URL`.** Without it, production enquiries cannot be stored.
2. **Set the email keys** (`RESEND_API_KEY`, `ENQUIRY_NOTIFICATION_EMAIL`, and
   `ENQUIRY_FROM_EMAIL` once the studio's domain is verified with Resend), so
   the studio is alerted to new enquiries. Verify the sending domain with
   SPF/DKIM records, then send a test enquiry to confirm delivery.
3. **Set `ADMIN_ACCESS_TOKEN`** (long and random: `openssl rand -hex 32`) and
   keep the URL private. Set `CALENDAR_FEED_TOKEN` too, subscribe to the feed
   once on the studio's phone or calendar app, and send a test request to
   confirm the slot appears.
4. **Confirm the domain in `NEXT_PUBLIC_SITE_URL`.** The default in this build
   is `https://www.magmenscouture.com` as a placeholder; change it if the live
   domain differs. Canonical URLs, the sitemap and social previews all use it.
5. **Founder portrait.** The founder section currently shows the studio's logo
   as a brand plate. A portrait would be stronger — see "Add the founder
   portrait" above.
6. **Approved testimonials.** None were supplied, so the client-experience
   section says so honestly instead of inventing reviews.
7. **Business hours.** Not supplied, so they appear nowhere — including in
   structured data.
8. **Review the privacy notice** in `src/content/privacy.ts`. It describes what
   this build actually does (the form fields, storage in Neon, notifications via
   Resend, no advertising or analytics cookies, an IP-derived key used only to
   limit abuse). Confirm the retention wording and the contact route match
   studio practice, and update the version/date if anything changes.
9. **Verify the social links.** Instagram, Facebook and TikTok URLs in
   `src/content/site.ts` were located during research; confirm each is the
   studio's current profile.
10. **Structured data.** `LocalBusiness`/`ClothingStore` carries only verified
    facts — name, description, slogan, telephone, address, founder and founding
    year. No ratings, review counts, prices or opening hours are published,
    because none were supplied.
11. **Consider a Google Business Profile** for "bridal designer in Obuasi"
    searches; the structured data already matches the site's stated details.

### One name to confirm

Public reporting credits the founder as **Marian Gifty Mensah**, married name
Dosaah. The website uses the name supplied in the brand brief — *Mrs. Marian
Gifty Mensah-Dossah*. Confirm the preferred published form and change it once in
`src/content/site.ts` and `src/content/story.ts`; it also feeds the structured
data.

The nine awards and recognitions shown on the founder page are the studio's own
supplied list, reproduced with their titles and awarding bodies intact.

## Deployment

The site is a standard Next.js application and builds cleanly for any Node host.
Vercel is the lowest-friction option and is what the steps below assume.

### What must be committed

`public/photography`, `public/og` and `src/content/image-manifest.json` are
**generated, but committed**. The build reads them; it never runs the image
pipeline. `./photos` (the ~45 MB of originals) is committed too, so the pipeline
can be re-run for new work. Everything else that is generated or local —
`.next`, `node_modules`, `data`, `.env*` — is ignored.

### Before you deploy

```bash
npm run check      # typecheck + lint + production build
```

Then confirm the environment:

- `DATABASE_URL` is set — without it, form submissions return HTTP 503 on Vercel,
  because a serverless disk is read-only and the local file store cannot be used;
- `ADMIN_ACCESS_TOKEN` is long and random;
- `NEXT_PUBLIC_SITE_URL` is the live domain, so canonical URLs and the sitemap
  are correct.

### Steps

1. Push the repository to GitHub (or connect your preferred source).
2. Import it in Vercel. Framework preset: **Next.js**. Build command
   `npm run build`, install command `npm install`, Node 24 (pinned in
   `package.json`). No other overrides are needed — no environment variables are
   required just to build.
3. Add the environment variables from the table above. Set them for **both
   Production and Preview**, so a preview deploy is testable end to end.
4. Deploy a **preview** first, verify it, then promote to production.
5. Verify on the deployed URL:
   - every route returns 200 and unknown paths return the bespoke 404;
   - the hero photograph and gallery render, and the lightbox opens and closes
     with the keyboard (`Tab` to a photograph, `Enter`, then `←`/`→`/`Esc`);
   - a consultation request submitted from a phone is stored and arrives in the
     studio inbox, and appears at `/admin/enquiries?token=…`;
   - `/sitemap.xml` and `/robots.txt` show the production domain;
   - a social preview of the homepage renders the branded card.
6. Submit `https://<domain>/sitemap.xml` in Google Search Console.

### Region

`vercel.json` places the serverless functions in **`lhr1` (London)**, the
closest standard region to Accra for form submissions. **Create the Neon
database in the same region** — otherwise every enquiry crosses the Atlantic
twice. If you choose a different database region, change `regions` in
`vercel.json` to match it. Static pages are served from Vercel's edge network
regardless, so only the four form endpoints and the admin view are affected.

Nothing else in the project depends on Vercel-specific features.

## Accessibility, performance and SEO

**Accessibility.** Skip link; visible gold focus outlines on every control;
semantic landmarks and heading order; labelled form controls with
`aria-describedby` error links and an assertive error summary; the lightbox and
mobile menu are modal dialogs with Escape-to-close, focus trapping and focus
return; descriptive alt text on every photograph; native `<details>` for the
policy accordion so it works without JavaScript; and every animation is disabled
under `prefers-reduced-motion`.

**Performance.** Images are served through `next/image` in AVIF/WebP with blur
placeholders and explicit dimensions, so nothing shifts. Photography is
pre-optimised, fonts are self-hosted through `next/font` with `display: swap`,
and there are no third-party scripts or trackers — no analytics, no advertising
pixels, no external font or image CDNs.

**SEO.** Unique titles and descriptions per page; canonical URLs; Open Graph and
Twitter cards with per-photograph images; `sitemap.xml`; `robots.txt`; JSON-LD
for the business and the website; semantic HTML throughout; and descriptive
image file names (`bridal-ivory-ballgown-blossom.webp`) rather than camera
filenames.
